# ADR-0002: Use SQS (with a dead-letter queue) to move check results from probes to the core

- **Status:** Accepted
- **Date:** 2026-11-01
- **Deciders:** Aadi007-git

## Context

Probe workers in three regions produce check results (500/s at design scale, packed ~100 per message,
so ~5 messages/s). The core, in one region, must store and evaluate them.

The core will sometimes be **unavailable**: deployments, crashes, database maintenance, a bad release.
NFR8 says a result handed over by a probe must **never be silently lost**. NFR1 needs results to
reach the evaluator within seconds.

## Decision drivers

1. **Durability while the core is down** (NFR8).
2. **Absorb spikes** so the core can be sized for the average, not the peak.
3. **Low cost and no servers to run:** a one-person team, cost NFR11.
4. Lets us **scale consumers** with backlog (KEDA, Step 3.3).
5. Simple for probes running on Lambda in other regions to use.

## Options considered

### Option A: Direct HTTP (probes POST results to the core API)
- ✅ Fewest moving parts; easy to trace.
- ❌ When the core is down or being deployed, results are lost unless every probe builds its own
  buffer-and-retry logic.
- ❌ Spikes hit the API directly; **temporal coupling**: probes and core must be up at the same time.

### Option B: Amazon SQS (standard queue) + dead-letter queue
- ✅ Fully managed and serverless; keeps messages up to **14 days**; scales automatically.
- ✅ Built-in **dead-letter queue (DLQ)**: a message that fails 5 times is set aside for inspection
  instead of blocking the queue or vanishing.
- ✅ Pennies at our volume; KEDA has a ready-made SQS scaler; cross-region sends from Lambda are simple.
- ❌ **At-least-once delivery:** a message can arrive more than once, so the ingestor must be
  **idempotent** (de-duplicate by `check_id`).
- ❌ **No ordering guarantee:** results carry their own timestamps, and the evaluator groups by
  scheduled minute rather than arrival order.

### Option C: Kafka (Amazon MSK or self-hosted)
- ✅ Ordering per partition, replay, many independent consumer groups, huge throughput.
- ❌ Brokers to run and pay for 24/7 (hundreds of dollars a month), for ~5 messages/s.
- ❌ Significant operational complexity (partitions, consumer offsets, broker upgrades).

### Option D: Amazon EventBridge
- ✅ Great for routing one event to many different targets.
- ❌ Built to push events to targets, not to act as a pull-based work queue with backlog-based scaling.

## Decision

**Option B: SQS standard queue with a dead-letter queue**, in the core region. It meets durability
and spike absorption (drivers 1–2) with no servers to run and negligible cost (driver 3), works
directly with KEDA (driver 4), and is trivial for Lambda workers in any region to call (driver 5).

## Consequences

- **Positive:** a core outage only delays processing; it loses nothing (up to 14 days). Ingestors
  scale with queue depth. Bad messages are isolated in the DLQ.
- **Negative (accepted):** consumers must be idempotent; the ingestor deletes a message only
  **after** the database commit; ordering is handled in our own logic.
- **Follow-ups:**
  - LLD: `check_id` (a UUID generated by the worker) is the de-duplication key.
  - Alert on **DLQ depth > 0** and on **age of the oldest message** (Step 3.2).
  - Define a message schema with a version field and test it with a contract test (Step 1.7).

## Revisit when

- Several **independent consumers** need the same stream (analytics, ML, billing), or we need
  **replay**. That points to Kafka or Kinesis.
- **Strict ordering** becomes a requirement. That points to SQS FIFO or Kafka.
- Volume grows to the point where per-request pricing beats the cost of a streaming platform.
